## Workloadbasis uit de repository

- `docker-compose.yml`: postgres:16-alpine (limits 2 CPU / 4 GB, external volume, 127.0.0.1-bound), redis:7 (0.5 CPU / 256 MB), manticoresearch 6.3.8 (1 CPU / 1 GB, named volume `manticore_data`), `server` (Bun/Hono/tRPC :3000), `web` (Next.js :3001).
- `docs/runbooks/postgres-on-box.md`: production gate = wal-g continuous WAL to a separate S3-compatible off-site bucket, daily base backup, 7-day PITR, restore drill RPO ≤ 1 h / RTO ≤ 4 h, monthly drill in P0. Start budget on a **32 GB / 8 vCPU** host: Postgres 8 GB reserved (12–14 GB / 4 vCPU cap), Manticore 8 GB / 2–2.5 vCPU, app+workers 4 GB, ≥ 6 GB page cache.
- `docs/adr/ADR-0004`: Postgres 16 on-box in Docker is the decision; managed Postgres is an explicit escape hatch only when HA, RTO/RPO, or contention evidence demands it. **Achterhaald op 2026-08-31:** [ADR-0006](../adr/ADR-0006-neon-as-system-of-record.md) kiest Neon als production SoR; de on-box-Postgres-aannames in dit rapport (incl. de aanbeveling "compose lokaal → Coolify op Hetzner" met Postgres op de box) gelden alleen nog voor Manticore/apps, niet voor de database.
- `docs/runbooks/coolify-local.md`: Coolify apps `server` (Dockerfile, /readyz) + `web`, Postgres 16 service, one-shot migrator job.
- `de interne kostenkaart`: P0 = 200k aanvragen/mnd, year-1 ceiling 600k/mnd, ~1–1.2 M fetches/mnd, corpus 7.5 M docs after 12 months; Trigger.dev Cloud, Upstash, Firecrawl etc. are constant across hosting options and excluded below.
- **Correctie op `de interne kostenkaart`:** de regel "Hetzner Cloud CCX33 … €43,49/mnd" is onjuist. €43.49 is **CCX13 (2 dedicated vCPU / 8 GB)**; **CCX33 (8 vCPU / 32 GB) is €138.99** (Hetzner price API, zie hieronder). Het P0-infrabedrag van €210 en de toets aan de NFR "< €300" waren op de verkeerde box gebaseerd.

## Opties

### 1. Hetzner on-box via Coolify

- **Residency:** FSN1/NBG1 (DE) or HEL1 (FI); no NL location, but EU/AVG-compliant with a German processor; Object Storage in eu-central. Hetzner is an EU company (no CLOUD Act exposure).
- **Backups/WAL/restore:** entirely yours — the repo already specifies wal-g → S3-compatible bucket (Hetzner Object Storage €6.49 covers < 1 TB), daily base, 7-day PITR, monthly restore drill. Hetzner's +20% Backups and €0.0143/GB snapshots are crash-consistent server images, useful as a second layer, not a Postgres backup. No managed HA; real HA = second box + Patroni/repmgr (ops cost, not € cost) or Ubicloud ($78–156, standby pricing unpublished).
- **Manticore:** best fit — local NVMe volume, mmap-friendly, RT tables persist across container replacement. Rebuildable from Postgres, so a search-box outage is not data loss.
- **Ops burden:** highest. You own kernel/Docker/Coolify updates, firewall (5432 never public — runbook), disk alerts, restore drills, TLS via Coolify proxy. For 1–2 people this is the tax you pay for the price.
- **Lock-in / migration:** zero from the current compose stack — Coolify deploys the same Dockerfiles. Moving away later = moving containers + pg_basebackup/wal-g restore.
- **Hidden costs:** volume price rose 30% in Apr 2026 (€0.0572/GB — 2 TB = €114/mo, more than a CCX23); IPv4 €0.50; CX plans are stock-limited ("not available" flags on the page) — budget CPX/CCX; dedicated AX has setup fees (€39–49) and monthly cancellation notice; no per-seat or minimum billing.
- **PoC → C without migration:** vertical resize of the same VM (CX43 → CX53 → CCX33 → CCX43) is a reboot, not a migration; volumes resize online. Step-costs: shared→dedicated (€30 → €139), CCX43 €276 → AX102 dedicated €159–259 (cheaper per core but a server move). Multi-tenancy (one box, one Postgres with per-platform databases, one Manticore with several RT tables) is clearly cheaper than one stack per platform: a second full stack adds ≥ €185 each; a second database on the same instance adds only storage.

### 2. Railway

- **Residency:** EU West Metal = Amsterdam (`europe-west4-drams3a`); volumes and backups stay in-region. Railway is a US company → DPA + SCCs and a CLOUD Act note in the DPIA.
- **Backups/WAL/restore:** Postgres template is explicitly "unmanaged"; Railway offers **volume snapshots** (daily 6-day / weekly 1-month / monthly 3-month, CoW, billed per incremental GB). No WAL archiving, no PITR, no HA. To meet the runbook you still run wal-g in a sidecar and pay $0.05/GB egress to an external bucket; restore drills are manual (spin a second Postgres service, restore, point a temp API at it — workable). Volume can only mount to one service — a restore target needs its own volume.
- **Manticore:** works (persistent volume, single replica). RAM is the cost driver — Manticore's RT table memory is billed at $10/GB.
- **Ops burden:** low — no OS, git-push deploys, Dockerfiles reused as-is, private networking between services, TCP proxy for Postgres access. You still own Postgres tuning, upgrades (image bump), and backup verification.
- **Lock-in / migration:** low. Same Docker images; config via env vars; `railway.json` optional. Compose → Railway is mostly re-declaring env/volumes; back out by pulling volumes via backup or pg_dump.
- **Hidden costs:** Hobby's 5 GB volume cap forces Pro at ~20 GB of data; usage-based billing spikes if the worker or Manticore pegs CPU (a 4-vCPU burst for a month = $80); egress $0.05/GB incl. Postgres TCP proxy; **Railway bills RAM on actual usage, so a JVM-style memory hog costs immediately** — but there is no per-seat fee and no minimum beyond the $20 credit.
- **PoC → C without migration:** add services (each platform = 3 more services) and resize Postgres/Manticore in place; no re-architecture. Step-costs are linear per vCPU/GB, so C ends ~1.5× Hetzner; the price of a shared 4 vCPU/16 GB Postgres ($240) is roughly one whole Hetzner app+DB layout. Multi-tenancy (shared Postgres + Manticore, per-platform api/web/worker) is cheaper than N stacks because the DB/search services dominate the bill; only the stateless services scale linearly.

### 3. Encore Cloud + GCP

- **Residency:** GCP europe-west4 (Eemshaven, NL) for all data-plane resources; Encore's control plane (build, tracing events, logs 30 days on Pro) runs on Encore's infrastructure — region not stated on the pages read; confirm before AVG sign-off.
- **Backups/WAL/restore:** inherits Cloud SQL — automated daily backups (7 days) and PITR per Encore's GCP docs; HA is a Cloud SQL flag (×2 price). Off-platform copy = scheduled `gcloud sql export` to GCS; restore drill = clone instance (billed by the hour).
- **Manticore:** **not an Encore primitive.** Options: GCE VM (e2-medium ≈ $27 + disk) managed outside Encore, with the endpoint/secret injected as an Encore secret — recommended; or Cloud Run with a GCS FUSE volume (not POSIX-safe for searchd's mmap/fsync; not recommended); Filestore volumes have a 1 TiB minimum capacity and are uneconomic here. Either way Manticore sits outside Encore's infra graph, preview environments, and tracing.
- **Ops burden:** lowest for what Encore owns (Cloud Run, Cloud SQL, Memorystore, Pub/Sub, GCS, cron, secrets, previews per PR, tracing). Anything else (Manticore VM, Next.js web hosting — Encore Cloud does not host a Next.js SSR app; you'd deploy `web` to Cloud Run yourself or Vercel) is yours.
- **Lock-in / migration effort — the honest part:** Encore.ts is a framework, not a deployer. APIs must be declared with `api()` from `encore.dev/api`; raw endpoints give a Node `(req, res)` handler, so a Hono+tRPC router could be bridged behind a catch-all raw endpoint, but then Encore's typed clients, validation, and per-endpoint tracing (the reasons to use it) are lost. Encore's FAQ: "libraries that own the HTTP server, process lifecycle, or infrastructure connection may need an Encore-specific integration." Runtime is **Node.js**; the FAQ says Bun/Deno support is "on the way" and `@encore.dev/bun-runtime` on npm is a 2024 nightly — assume no Bun. Drizzle works (Encore exposes a connection string). Worker polling maps to Encore cron + Pub/Sub. Realistic effort for this repo: rewrite the server package's HTTP layer and infra wiring (1–3 weeks for 1–2 people), drop Bun-specific APIs, keep Trigger.dev as-is. Exit path exists (`encore build docker` + your own infra-config), but the code stays Encore-shaped.
- **Hidden costs:** per-seat ($49/member), per-environment ($99 each — staging/prod = $198 before any cloud spend), per-resource ($2.50 × resources × environments — secrets count), Encore-forced Memorystore HA (Standard tier, +$25–63/mo over Basic), Cloud SQL "smallest available" default may be shared-core with no SLA — check what it provisions, and GCP egress at $0.12/GiB.
- **PoC → C without migration:** one Encore app, many services, one GCP environment; adding a platform = adding services/databases in code (Encore provisions them). Databases declared per service land on the environment's Cloud SQL instance(s) — verify whether Encore consolidates onto one instance; if it provisions one instance per database, C roughly doubles. Step-costs: Cloud SQL tier jumps (1→2→4 vCPU HA: $54 → $217 → $445 + storage) and the $2.50 × resources × envs fee growing with every platform. Multi-tenancy is cheaper than separate Encore apps (which would each need their own $99 environments), but the per-resource fee makes every added platform cost ~$25–50/mo in control-plane fees alone.

### 4. GCP direct (Cloud Run + Cloud SQL)

- **Residency:** europe-west4 (NL). Google is a US provider → SCCs/CLOUD Act note; EU data boundary controls available on paid support tiers.
- **Backups/WAL/restore:** Cloud SQL automated backups + 7-day PITR (backups $0.088/GiB-mo), on-demand backups, clone-for-drill; cross-region backup copies configurable; export to GCS for an off-Google copy. This is the strongest managed backup story of the four with the least code.
- **Manticore:** same as option 3 — a GCE VM with pd-balanced disk; Cloud Run is a poor fit for a stateful search daemon.
- **Ops burden:** medium-low. Cloud Run + Cloud Scheduler + Cloud SQL + Secret Manager are managed; you own IAM, VPC connector/Direct VPC egress for Cloud SQL private IP, the Manticore VM, and Terraform/gcloud scripts (this is what Encore would generate for you).
- **Lock-in / migration:** Docker images reused (Bun stays — Cloud Run runs any container). Cloud SQL is vanilla Postgres 16 (pg_dump/logical replication out). Migration from compose = writing the deploy config (Terraform or `gcloud run deploy`) and re-pointing DATABASE_URL.
- **Hidden costs:** egress $0.12/GiB Premium (Standard tier 200 GiB free then $0.085); Memorystore's $37/GiB-mo floor (use Upstash or Redis on the Manticore VM instead); Cloud SQL HA doubles compute and storage; minimum 1 vCPU when CPU is always allocated (fractional CPU only with request-based billing); external IPs $3.65 each; Cloud NAT if the worker needs a static egress IP for source allow-listing (~$32/mo + processing, not included above). No per-seat fees.
- **PoC → C without migration:** add Cloud Run services per platform; resize Cloud SQL in place (restart) and add databases on the same instance; Manticore VM resize. Step-costs: Cloud SQL tiers (each doubling ≈ +$100–230/mo with HA) and HA SSD at $0.374/GiB-mo (2 TB ≈ $750/mo vs €114 on Hetzner). Multi-tenancy on one Cloud SQL instance is far cheaper than per-platform instances; Cloud Run services are cheap enough that per-platform api/web/worker is fine.

## Aanbeveling (team van 1–2 mensen, eerst lokaal verifiëren, later migreren)

Blijf bij het huidige plan: **compose lokaal → Coolify op Hetzner**, maar budgetteer het correct — de 32 GB/8 vCPU-box uit het runbook is **CCX33 voor €138.99, niet €43.49**, dus P0-infra met back-ups is ~€185/maand, nog steeds onder de NFR van €300 en ~5–8× goedkoper dan elk managed pad met dezelfde capaciteit. Start op een CX43/CPX32 (€16–36) zolang het corpus klein is, resize in place wanneer Postgres en Manticore concurreren, en laat de bestaande wal-g → Object Storage-gate plus een maandelijkse restore drill het "HA"-verhaal zijn totdat de escape-hatch-evidence uit ADR-0004 verschijnt; als dat gebeurt, is **Ubicloud managed Postgres on Hetzner ($78–156, PITR included, same German DC)** de goedkoopste HA-stap waarbij de rest van de box onaangeroerd blijft. Railway is de juiste tweede keuze als ops-tijd, niet geld, de beperking wordt — dezelfde Docker-images, Amsterdam-regio, ~€100–200/maand voor JI, maar de WAL-sidecar blijft nodig en op multi-platform-RAM-niveau wordt het duur. Sla Encore over voor deze codebase: de waarde ervan (typed infra + provisioning) vereist dat Bun/Hono/tRPC wordt verlaten en ~€195–500/maand aan control-plane-fees voordat er één GCP-factuur is, terwijl Manticore en Next.js er sowieso buiten vallen; als GCP's Cloud SQL-back-up/HA-verhaal later gewenst is, kies dan **GCP direct** met dezelfde containers (~€105 PoC, ~€430 met HA). Multi-tenancy (één Postgres, één Manticore, stateless services per platform) is op elke provider de goedkopere vorm; het groeipad is verticaal op Hetzner (CX → CCX → AX, geen migratie) en blijft in de fase met 3–5 platforms 1.5× goedkoper dan Railway en 2–3× goedkoper dan GCP/Encore.
